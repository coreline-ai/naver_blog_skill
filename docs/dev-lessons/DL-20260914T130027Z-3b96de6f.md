# 파생 준비 상태는 요약 보고서가 아니라 정본 산출물에서 재계산한다

## 적용 범위와 비적용 조건

정본 산출물과 별도의 보고서에 ready, queue, count 같은 파생 상태를 저장하는 로컬 준비·배포·실행 패키지에 적용한다. 전자서명이나 원격 신뢰 저장소를 대신하는 규칙은 아니다.

## 관측 사실과 영향

시각 계약 위반으로 blocked인 v2 준비 패키지에서 series-report.json의 상태와 readiness를 ready로 바꾸고 snapshot 해시를 다시 계산하자 기존 status가 integrity=passed와 ready queue를 반환했다. 실제 canonical post와 preflight 진단은 계속 blocked 상태였다.

## 근본 원인·기여 요인·근거

snapshot 검증이 파일 해시와 report 내부의 status, queue, totals 일관성은 확인했지만 report의 파생 필드를 canonical post, asset integrity, content metrics, preflight review 결과와 교차 검증하지 않았다. 동일한 비신뢰 요약값으로 다시 계산한 자기 일관성 검사가 정본 기반 검증을 대신했다.

## 해결과 예방 control

파생 readiness는 하나의 결정적 함수에서 계산하고 prepare와 status가 같은 구현을 사용한다. snapshot 조회 시 canonical post, asset integrity, content metrics, visual binding, review 진단을 다시 읽어 report의 상태·오류·글자 수·불리언·queue·totals와 비교하며 불일치는 CORRUPT_SNAPSHOT으로 거부한다.

## 검증

tests/test_prepare_series_v2.py의 report 재작성, 2,999자 위조, metrics/preflight 불일치 회귀 테스트가 재해시한 snapshot을 거부한다. 전체 Python 테스트와 Node SmartEditor 테스트, 두 스킬 quick validation을 함께 실행해 v1과 실행 이력 회귀가 없음을 확인했다.

## 발생 정보

2026-09-14 로컬 synthetic fixture에서 발견했다. 실사용 발행이나 원격 데이터 변경은 수행하지 않았으며, 수정 전 임시 조치는 준비 산출물을 수동 변경하지 않고 새 run-id로 재생성하는 것이었다.

## 검토와 예외

요약 필드를 새로 추가하거나 readiness 조건을 변경할 때 정본 기반 재계산과 report 불일치 테스트를 함께 추가한다. SHA-256 파일 목록은 변경 감지 수단일 뿐 작성자 인증이나 로컬 관리자 공격 방어로 표현하지 않는다.
