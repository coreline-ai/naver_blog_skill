## 작성 프로필 계약

| 프로필 | 기본 목적 | 필수 콘텐츠 자산 | 이미지 목표 | 핵심 금지 |
|---|---|---|---:|---|
| `expert` | 기술·원리·제도·전문 가이드 | 용어 정의, 메커니즘 2개 이상, 조건부 예제, 진단/비교 도구, 절차, 예외·한계, 주장-출처 연결 | 5 | 근거 없는 단정, 수치의 보편화 |
| `story` | 시행착오와 변화 과정을 통한 정보 전달 | 시작 상황, 문제, 시도, 예상 밖 결과, 전환점, 해결, 독자 적용 원칙 | 4 | 제공되지 않은 1인칭 체험 |
| `review` | 실제 제품·장소·서비스 사용 평가 | 사용 조건, 기간·환경, 선택 이유, 사용 과정, 장단점, 적합/부적합 대상, 최종 판단 | 5~7 | 생성 이미지를 체험 증거로 사용 |
| `friendly` | 초보자가 이해하는 쉬운 설명 | 즉답, 쉬운 비유, 단계별 설명, 흔한 실수, 체크리스트 | 3~4 | 유아적 표현, 정확성 생략 |
| `troubleshooting` | 증상과 원인을 좁혀 해결 | 증상 정의, 우선 원인, 자가 진단, 원인별 조치, 확인법, 중단 조건, 재발 방지 | 4~5 | 한 증상을 한 원인으로 단정 |
| `comparison` | 두 개 이상의 선택지 결정 | 비교 조건, 평가 기준, 대칭 비교표, 상황별 적합성, 선택 체크리스트 | 4~5 | 근거 없는 승자 선정 |

한 원고에는 주 프로필 하나와 보조 프로필 하나만 허용한다. `expert+friendly`를 기본 조합으로 하며, 현재 요청의 명시적 스타일이 최우선이다.

## 신규 v2 계약 초안

```json
{
  "schema": "naver-series/v2",
  "requirements": {
    "content_mode": "full_article",
    "primary_style": "expert",
    "secondary_style": "friendly",
    "min_body_chars": 3000,
    "visual_mode": "required",
    "min_images_per_episode": 3,
    "target_images_per_episode": 5,
    "tag_line_max_chars": 100
  }
}
```

### 값 결정 우선순위

1. 현재 사용자 요청의 명시 값
2. 현재 시리즈 manifest에 확정된 값
3. 같은 실행의 저장된 요구사항
4. 선택된 작성 프로필 기본값
5. 전역 완성형 기본값

이 우선순위로 이전 대화에 5장이 확정된 실행을 임의로 1장으로 낮추는 문제를 차단한다.

### 본문 글자 수 산정

`body_char_count`는 다음 순서로 계산한다.

1. 공개용 article Markdown을 읽는다.
2. H1 제목, 태그 영역, 참고자료 URL, 이미지 마커·링크, alt, caption, 편집 메모를 제거한다.
3. H2/H3, 일반 문단, 인용구, 목록, 표의 공개 텍스트는 유지한다.
4. Unicode를 정규화하고 연속 공백·개행을 한 칸으로 축약한다.
5. 결과 문자열의 Unicode code point 수를 계산한다.

`2,999`는 실패, `3,000`은 길이 기준 통과, `3,001`은 통과다. 길이 통과는 편집 품질 통과를 뜻하지 않는다.

### 이미지 수량 판정

- `approved` 상태이고 실제 디코딩 가능한 파일만 센다.
- 파일 내용 해시가 같은 이미지는 한 장으로 센다.
- 대표 이미지 1장과 inline 이미지 2장 이상을 요구한다.
- 최소 3장을 충족하면 `visual_minimum_met=true`다.
- 스타일 목표를 충족하면 `visual_target_met=true`다.
- 최소는 충족했지만 목표가 부족하면 경고를 남길 수 있으나, 생성 단계에서는 목표 수량을 우선 완료한다.
- 관련성·오류·권리 검수에 실패한 파일은 수량에서 제외한다.

## 공통 진행 규칙

- 각 Phase는 앞선 Phase의 자체 테스트 완료 후에만 시작한다.
- 구현 중 발생한 이슈는 해당 Phase에서 수정하고 기록한다.
- 체크박스 상태를 실제 진행 상태와 맞게 업데이트한다.
- 문서에 없는 범위 확장은 하지 않는다.
- 요구사항이 불명확하면 가능한 케이스를 나누고 확인 후 진행한다.
- 한 기능은 유지보수 가능한 최소 책임 단위로 나누고 역할과 경계를 지킨다.
- 공통화는 이번 범위 안의 중복을 줄일 때만 수행하며 새 프레임워크를 도입하지 않는다.
