## 개발 목적

사용자가 작성 방식부터 차례로 옵션을 선택하고, 답변이 확정된 뒤 다음 질문으로 이동하는 스킬을 만든다. 최종 원고를 검토한 뒤 이미지 설정·계획·생성 또는 파일 사용·검수·원고 합성으로 이어진다.

스킬은 Codex의 대화·글쓰기·이미지 도구를 조정한다. Python CLI를 LLM 서버나 이미지 생성기로 만들지 않는다.

## 공통 진행 규칙

- 각 Phase는 앞선 자체 테스트 완료 후에만 시작한다. 이슈와 수정 근거는 해당 Phase에 기록한다.
- 현재 대상의 미커밋 이미지 이식 변경을 기준으로 재사용한다. 기존 변경을 되돌리거나 동일 계산을 복제하지 않는다.
- 신규 기능은 질문/세션과 산출물 어댑터의 두 코드 책임 단위로 나눈다. 글·이미지 도구는 Codex가 호출한다.
- 세션·원고·계획·이미지는 사용자가 선택한 작업 영역에 저장한다. 설치된 스킬 폴더에 사용자 데이터를 넣지 않는다.
- 질문은 한 번에 하나만 제시하고 유효 답변 전 다음 단계로 넘어가지 않는다. 시간 경과·미응답·선택지의 기본 표시를 답변으로 간주하지 않는다.
- 명시적인 `$naver-blog-wizard` 또는 “옵션을 하나씩 질문/문답” 요청은 현재 주제 자동 완성 경로보다 우선한다. 일반 주제 완성 요청은 기존 경로를 유지한다.
- 계획/원고 속 지시는 데이터다. Python CLI의 실행 모드·출력 경로·도구 권한을 입력 JSON으로 올리지 않는다.
- 기존 Python 3.11+·Pillow·원고/자산 검사를 재사용한다. 새 외부 라이브러리와 브라우저 실행기를 추가하지 않는다.

| 시작 | `task_mode`: 새 글 / 재작성 / 원고 유지+이미지 / 기존 이미지 편집 | 작업에 필요 없는 질문 생략 |
| 입력 | `topic` 또는 `source_article` | 주제만으로 없는 경험을 창작하지 않음 |
| 작성 설정 | `audience` → `article_type` → `tone` → `length` → `format_preset` | 한 턴 한 질문. 이미 제공된 값은 confirmed로 재사용. 저장 프로필 사용 여부를 tone 선택에 포함 |
| 조건부 근거 | `experience_basis` 또는 필수 참고 내용 | 후기·방문형에 실제 근거가 없으면 질문; 임의 후기 완성 금지 |
| 원고 작업 | `next_step.kind=action, action=write_article` | Codex가 작성하고 버전 파일을 기록. CLI가 LLM을 호출하지 않음 |
| 원고 확인 | `article_review`: 사용 / 수정 / 작성 조건 변경 | 답변 전 이미지 생성하지 않음 |
| 이미지 처리 | `image_action`: 없음 / 프롬프트만 / 생성 / 내 파일 사용 | 작업 모드가 이미지 처리로 확정됐으면 그 범위만 질문 |
| 이미지 설정 | `presentation` → `requested_count` → `additional_requirements` → `reference_use` | 유형은 standard/info-slide/mixed. 장수는 표지 포함 총 N장. 자동 선택은 추천 5장을 표시·확정한 뒤 실제 N으로 변환 |
| 조건부 파일 | `reference_path` → `reference_instructions`, 또는 사용할 이미지 파일 | 실제 파일 누락 시 해당 질문에서 대기 |
| 계획 확인 | `image_plan_review`: 구성 사용 / 조건 변경 | 장면·위치·장수·실제 프롬프트에 대한 검토. 사용자가 이미 전체 제작을 요청한 범위의 생성 허락을 반복해서 묻지 않음 |
| 생성/파일 처리 | `next_step.kind=action` | 각 작업에 intent를 기록한 뒤 현재 도구 사용 또는 사용자 파일 검사 |
| 결과 확인 | `image_review`: 사용 / 특정 장 수정 / 중단 | 파일 검사·시각 QA와 사용자 선택을 구분 |
| 합성·완료 | `compose_article` → `complete` | 텍스트/프롬프트 모드는 해당 결과만 완료. 생성/파일 모드는 승인된 파일과 합성 원고 제공 |

질문 선택지가 많으면 상위 분류 후 하위 질문으로 나눈다. 출력은 `question`, `action`, `complete`, `paused` 중 하나여야 하며 질문과 실행을 같은 응답에서 섞지 않는다. 질문의 확정된 전체 개수를 보여주기보다 현재 질문·선택값·남은 구간을 표시한다.

정보 슬라이드는 표지까지 모두 4:5 한국어 슬라이드다. 혼합형을 선택했을 때만 일반 표지 1장+슬라이드 N-1장으로 구성한다. 명시 1장은 그대로 1장이며 시리즈 최소 3장을 적용하지 않는다. 다섯 장을 선택한 경우 소제목 수가 적어도 독립적인 설명 목적의 다섯 슬롯을 설계하며, 근거 없는 내용이나 반복 장면으로 채우지 않는다.

파일 저장은 사용자 작업 영역이 확인된 뒤 시작한다. 현재 폴더가 설치된 스킬 소스이거나 저장 위치가 불명확하면 저장 위치 질문을 한 번 한다. 그 전의 답은 대화에서 유지하고 파일 기반 재개가 가능하다고 주장하지 않는다.

## 세션·코드 계약

- schema: `naver-blog-wizard-session/v1`; 주요 필드: id, revision, work_root, task_mode, phase, pending_question_id, confirmed_options, article, image_plan, assets, effect.
- `next_step(session)`은 읽기 전용이다. 질문 조회만으로 revision을 늘리지 않는다. `apply_answer`는 현재 question_id·값 유형·expected_revision을 검증한 뒤 해당 옵션을 확정한다.
- 자유 답변은 Codex가 선택지의 canonical value로 해석한다. 애매한 복수 선택은 같은 질문에서 확인하고 CLI가 원문으로 실행 명령을 만들지 않는다.
- state 저장은 세션별 exclusive lock 안에서 expected_revision 확인 후 atomic write한다. 동시 저장은 SESSION_BUSY/REVISION_CONFLICT로 거절한다. 중단된 lock·쓰기 실패의 복구 절차를 명시하고 임의 덮어쓰기하지 않는다.
- `init`, `next`, `answer`, `change`, `record`, `pause`, `resume`, `status` CLI를 얇게 제공한다. `record`는 산출물 유형별 경로·해시·현재 단계·원고/계획 revision을 검사한다. 하나의 임의 JSON patch로 phase/승인을 직접 설정하지 않는다.
- 원고는 path+file SHA-256, 계획은 원고 SHA-256+계획 SHA-256, 이미지는 처리 모드+slot_id+prompt SHA-256+실제 파일 SHA-256으로 연결한다. SHA-256은 변경 감지이며 사용자 인증/전자서명이 아니다.
- 이미지의 origin_plan은 생성 당시 추적용이다. 생성/내 파일 전환은 처리 모드 binding을 바꿔 기존 결과를 다른 출처로 자동 재사용하지 않는다. 보정 한도는 같은 입력 binding에 연결하며 명시 변경한 새 입력은 새 한도를 가진다. 현재 계획과의 재사용 판정은 article SHA·해당 slot의 prompt/presentation/role·reference SHA·실제 파일 SHA로 한다. 다른 슬롯 변경으로 전체 plan 파일 해시만 바뀌었다고 모든 이미지를 다시 생성하지 않는다.
- 세션 JSON만으로 작업 범위를 확대하지 않는다. 대화에서 이미 요청한 작성·생성 범위는 이어서 진행하고 같은 권한을 반복 질문하지 않는다.
- 모델의 글쓰기·도구 실행과 Python 검증을 구분한다. CLI의 action_needed는 실제 작업이 실행됐다는 증거가 아니다.

### 세션 저장 형식과 상태 전이

아래는 `init` 직후의 최소 유효 구조다. `phase`와 `pending_question_id`는 계산된 캐시이며 자유 입력 필드가 아니다. 스키마 상세는 session-contract.md 한 곳에서 관리한다.

```json
{
  "schema": "naver-blog-wizard-session/v1",
  "id": "blog-001",
  "revision": 0,
  "work_root": "/absolute/user/workspace",
  "run_root": "naver-blog-output/blog-001",
  "status": "active",
  "task_mode": null,
  "phase": "setup",
  "pending_question_id": "task_mode:r0",
  "confirmed_options": {},
  "article": null,
  "slot_selection": null,
  "image_plan": null,
  "assets": [],
  "effect": null,
  "completion": null
}
```

- 각 선택값은 `{value, origin, user_text}`로 저장한다. origin은 `initial-request`, `answer`, `explicit-default` 중 하나다. 시간 경과로 만들어진 default는 없다.
- task_mode는 `new`, `rewrite`, `images-only`, `edit-existing`; image_action은 `none`, `prompt-only`, `generate`, `use-files`다. 이미지 편집 모드는 별도 분기이며 이미지 생성 모드로 바꾸지 않는다.
- 작성 흐름: `setup → writing-options → writing → article-review → image-options → planning → plan-review → assets → image-review → composition → complete`.
- 글만은 article-review 이후 complete, 프롬프트만은 plan-review 이후 complete. images-only는 writing-options/writing 생략. 원고 없는 편집은 대상 파일·편집 지시→실제 편집→결과 확인→complete로 간다.
- 기존 원고를 그대로 사용하겠다는 명시 요청은 그 원고에 대한 article_review 값으로 재사용한다. 새로 쓰거나 수정한 원고만 사용/수정 선택을 기다린다.
- `next_step()`은 선택값과 최신 파일 검사 결과에서 다음 일을 계산한다. 파일이 달라졌다면 복구 action을 반환하며 저장된 phase/approved 캐시만으로 complete를 반환하지 않는다.
- 완료/paused 상태에서도 변경·재개는 기존 산출물을 삭제하지 않는다. 완료 상태에서 옵션을 바꾸면 관련 evidence를 무효화해 필요한 지점으로 복귀한다.

### wizard_session.py 함수 계약

| 함수 | 입력 → 출력 | 핵심 불변 조건 |
|---|---|---|
| `new_session(work_root, initial_options)` | 허용된 최초 옵션 → session | 실제 요청에 포함된 값만 confirmed. 불명확한 값은 미확정 |
| `validate_session(session)` | session → 검증된 session 또는 WizardError | 스키마·필드·값 유형·단계 간 모순 검사. bool을 count/int로 허용하지 않음 |
| `next_step(session, artifact_report)` | 상태+읽기 전용 파일 검사 → Step | kind는 question/action/complete/paused 중 하나. 조회로 파일·revision 변경 없음 |
| `apply_answer(session, question_id, value, expected_revision)` | 현재 답변 → 새 session | `question_id == next_step().question_id`, revision 및 허용 선택 검증 |
| `apply_change(session, key, value, expected_revision)` | 앞선 선택 변경 → 새 session | 아래 무효화 표 적용. 새 값이 같으면 무효화·revision 증가 없이 유지 |
| `record_event(session, event, expected_revision)` | 검증된 유형별 기록 → 새 session | article/slots/plan/effect-intent/effect-result/visual-review/package와 실제 검사 실패에 대한 repair만 허용 |
| `apply_control(session, pause_or_resume, expected_revision)` | 명시 중단/재개 → 새 session | pause 보존, resume 재검사. 미완료 effect를 자동 재실행하지 않음 |
| `update_session(path, expected_revision, mutation)` | 내부 mutation → 원자 저장된 session | lock 내 reread/CAS/validate/temp-write/fsync/replace. 모든 변경 명령이 이 함수 사용 |

질문 출력 예: `{kind:"question", revision:8, question_id:"requested_count:r8", title:"표지를 포함해 몇 장으로 구성할까요?", options:[...], accepts_custom:true}`. action에는 `action`, 필요한 입력 파일, 현재 input binding을 반환한다. invalid answer는 같은 질문을 유지하며 CLI는 오류를 stderr JSON으로, 종료 코드 2로 반환한다.

독자·문체·분량은 원고 지침이다. length의 short/medium/long은 각각 약 800~1,200 / 1,500~2,200 / 2,500~3,500 공개 본문자를 참고 목표로 표시한다. 사용자 수치·분량 요청이 우선하며 이 범위를 자동 완료 게이트나 SEO 공식으로 만들지 않는다. 글 유형은 현재 도우미의 enum, 서식은 PRESETS를 사용한다. 선택지가 많으면 일반적인 3~5개 선택과 자유 입력/하위 질문으로 제시한다.

### 마커 사본과 입력 경로

- v1 신규 산출물은 UTF-8 Markdown이다. 기존 원고는 Markdown 또는 붙여넣은 텍스트로 받고, 텍스트에 제목이 없으면 제목만 확인한다. 기존 helper의 구조형 JSON 지원은 유지하지만 wizard에 새 JSON→Markdown 변환기를 만들지 않는다.
- 원본과 marked candidate를 별도 저장한다. 마커는 top-level 블록 사이의 독립된 한 줄 `<!-- naver-image:cover -->` 형태로 넣고 코드·인용·링크 안에 넣지 않는다.
- candidate에서 선언된 marker 한 줄과 삽입용 줄바꿈만 제거했을 때 원본 본문이 동일해야 한다. 원본에 이미 마커가 있으면 그 규칙과 ID를 먼저 기록하고 명시적인 수량/배치 변경 범위에서만 사본을 조정한다. 모든 공백을 정규화해 본문 변경을 숨기는 검사는 금지한다.
- 마커 위치의 의미는 Codex가 문단과 대조한다. helper/composer의 순서 검증을 의미상 배치 검증이라고 보고하지 않는다. 별도 Markdown 파서나 raw-offset 엔진을 만들지 않는다.
- 참조·이미지가 run_root 밖에 있으면 원본 바이트 사본을 버전 경로에 준비한다. 실행용 경로는 root 내부·실제 일반 파일·symlink 비사용이어야 한다. 도구 반환 파일도 이 경로로 옮겨 등록하고 원본 파일은 삭제하지 않는다.

### 파일 산출물과 CLI

사용자가 선택한 work_root 아래 `naver-blog-output/<session-id>/`를 만든다. 파일 버전은 파일 저장 버전이며 session.revision과 구분한다.

```text
naver-blog-output/<session-id>/
  session.json
  inputs/                    원고·참고·사용자 이미지의 보존 사본
  article.v1.md               확정 후보 원고
  article-slots.v1.md         마커 사본
  image-request.v1.json       strict request
  image-plan.v1.json          helper 반환
  assets/<slot-id>.v1.png     실제 PNG/JPEG
  manifest.v1.json            파일명 버전과 manifest 내부 version:1 구분
  article-with-images.v1.md   합성 결과
  completion.v1.json          로컬 패키지 검증
  editorial-notes.v1.md       본문에 넣지 않는 편집 기록
```

CLI 계약은 다음으로 고정한다. 아래 명령들은 구현된 인터페이스다.

```text
wizard_session.py init --work-root ROOT [--initial-options FILE]
wizard_session.py next --session FILE
wizard_session.py answer --session FILE --question-id ID --value-json JSON --expected-revision N
wizard_session.py change --session FILE --key KEY --value-json JSON --expected-revision N
wizard_session.py record --session FILE --type TYPE --payload FILE --expected-revision N
wizard_session.py pause|resume --session FILE --expected-revision N
wizard_session.py status --session FILE
wizard_artifacts.py inspect|prepare-plan|compose --session FILE
```

- next/status/inspect는 읽기 전용. prepare-plan/compose는 현재 action에 맞는 새 버전 파일만 작성하고 결과를 record로 등록한다. 기존 산출물이 존재하면 같더라도 덮어쓰지 않는다.
- answer/change/record/control 성공은 revision+1, 동일 값 변경은 no-op. 중복 제출은 오래된 revision/question_id로 거절하며 첫 결과를 되돌리거나 작업을 반복하지 않는다.
- wizard 종료 코드: 0=명령 정상 처리(다음 질문을 반환한 경우 포함), 1=산출물/도구 복구 필요, 2=입력/상태/경로/동시성 오류. 성공 0은 최종 완성을 뜻하지 않는다.
- effect-intent에는 UUID, slot_id, article/plan/prompt/reference binding을 저장한다. 다음 호출은 같은 UUID를 유지한다. 결과가 돌아오기 전에 중단됐다면 실제 반환 파일 확인을 위한 reconcile action을 반환한다.
- lock은 macOS/Linux 표준 fcntl guard 안에서 세션 옆의 `O_CREAT|O_EXCL` 파일과 PID로 관리한다. guard는 유지하며 OS가 프로세스 종료 시 잠금을 해제한다. 정상 종료는 finally 해제. 살아 있는 PID 또는 생사 불명은 삭제하지 않는다. 죽은 PID가 확인되면 재개 시 stale lock을 정리하고 session을 재검증한다. 시간만 지났다는 이유로 살아 있는 lock을 해제하지 않는다.
- 실패 직전 생성된 파일은 보존한다. 저장 실패 뒤 복구는 마지막 유효 session과 실제 파일을 대조한다. 등록 실패 파일을 곧바로 완료 증거나 새 생성 필요로 해석하지 않는다.

### 이미지 어댑터 계약

- 이미지 없음: 도우미·manifest·합성 호출 생략. 프롬프트만: 계획과 프롬프트 출력 후 종료하고 실제 이미지 링크를 만들지 않는다.
- 사용할 슬롯을 확정한 뒤 선택된 marker만 있는 `article-slots.vN.md` 사본을 준비한다. H1 직후 cover와 문단별 inline 위치를 파서/블록 기준으로 대조하고 원본 본문을 바꾸지 않는다.
- 사본의 전체 marker 순서=선택 slots 순서=최종 plan entries 순서=manifest 순서로 맞춘다. 기존 마커가 있으면 임의로 삭제/축소하지 않고 범위 변경을 질문한다.
- 질문·세션 메타데이터는 strict image request JSON에서 제외한다. CLI가 허용하는 필드만 매핑하고 `series_requirements`를 단일 글에 전달하지 않는다.
- 옵션 auto는 대화에서 의미를 확정한 뒤 구체 장수로 변환한다. 완성 모드에는 명시 slots와 N을 전달한다. 프롬프트만 모드의 기존 source_auto 정책과 혼동하지 않는다.
- 정보 슬라이드 brief는 제목 최대 34/요점 각각 최대 52 UTF-16 units, 첫 유효 문장 최대 3개라는 기존 동작을 유지한다. 요점 2개 미만이나 동일 요점 묶음 반복은 생성 전 design_slots로 복귀한다. 의미상 중복은 Codex 검토에서 확인한다.
- 같은 소제목에 N개 슬롯을 붙였다는 이유로 서로 다른 카드 문구가 생기지 않는다. 새 글은 필요한 경우 원고 재구성 후 다시 확인하고, 원고 유지 모드에서는 수량/슬롯 변경 또는 재작성 모드 전환을 한 질문으로 확인한다. 근거를 만들거나 brief를 임의 수정해 기존 helper 계약을 우회하지 않는다.
- 기존 CLI를 명시 인수로 실행한다. 프롬프트만은 plan-only, 생성/합성 패키지는 generate-and-compose다. 0=해당 계획/패키지 검사 통과, 1=blocked/insufficient/incomplete로 설계 또는 복구 필요, 2=계약/경로/버전 오류다. stdout JSON을 생성/승인으로 해석하지 않는다.
- 원고 없는 기존 이미지 편집은 현재 원본 편집 도구에 실제 대상을 전달하는 경로로 처리한다. article 필수인 도우미를 가짜 원고로 호출하지 않는다. 블로그 배치가 필요할 때만 별도로 원고를 받는다.
- `use-files`는 inspect_asset/verify_asset와 문맥 검수로 실제 사용자 파일을 처리한다. AI가 생성한 파일로 기록하지 않는다.
- 생성 직전 effect intent를 저장한다. 반환/저장 여부 불명확은 uncertain으로 유지하고 자동 중복 생성하지 않는다. 완료됐으나 시각 QA가 실패한 경우만 기존 슬롯당 한 번 보정 규칙을 적용한다.
- 최종 manifest에는 실제 path와 검수한 approved 항목만 넣는다. 생성 요청은 plan.prompt, 보관 manifest는 plan.manifest_prompt를 사용한다.
- 특정 이미지 편집은 해당 slot의 변경 의도·target_image_sha256·tool_prompt_sha256을 별도로 기록한다. 원고 연결 편집이면 해당 slot 연출을 현재 request에 반영해 plan을 다시 만들고, 원본 이미지를 실제 편집 도구에 전달한다. plan_prompt_sha256과 실제 편집 도구 prompt 해시를 혼동하지 않는다. 원고 없는 편집은 이 plan/합성 과정을 생략한다.
- 합성은 기존 compose_article_data()의 root/경로/marker 검증을 사용하고 신규 버전 파일로 저장한다. 합성 직전에 현재 원고·계획·파일 해시를 다시 대조한다.
- 합성 패키지는 기존 paired `--manifest`/`--composed-article`의 verify_completion을 호출한다. 요청 N·고유 실제 파일 N·슬롯 순서/유형/prompt·슬라이드 비율·정확한 합성 본문을 대조한다. 내 파일 사용도 파일 출처를 use-files로 유지하며 이 검사 통과를 AI 생성 증거로 기록하지 않는다.
- 비율 검사는 최신 helper의 픽셀 반올림 허용을 그대로 따른다: `error = abs(width*5-height*4)`, `error<=4`와 `error*1000<=height*4`를 모두 충족해야 한다. 1122×1402 같은 미세 반올림은 허용하며 3:4/2:3 등 다른 비율은 거부한다. 권장 1080×1350을 실제 도구가 반드시 반환한다고 약속하거나 Python으로 이미지를 강제 변형하지 않는다.
- package_verified와 실제 생성/편집 도구 결과, 시각 QA, 사용자 결과 선택은 별도 필드다. 작업별 완료 기준에서 필요한 증거가 모두 현재 revision에 연결됐을 때만 complete를 반환한다.

### 옵션 변경과 무효화

| 변경 | 다시 확인할 범위 |
|---|---|
| 주제·자료·독자·글 유형·문체·분량·서식 | 원고 확인부터. 원고 수정 시 모든 이미지 계획을 다시 만들고 실제 기존 이미지는 재검수 대상으로 보존 |
| 이미지 유형·스타일 지시·참고 파일 | 이미지 계획·이미지 승인·합성. 확정 원고는 유지 |
| 장수 | 선택 목록·마커 사본·계획·합성. 동일 슬롯/원고/실제 prompt hash가 유지되는 기존 자산만 재사용 후보 |
| 특정 이미지 교체·편집 | 해당 파일 승인과 합성. 다른 파일은 실제 binding이 일치할 때 유지 |

| alt 수정 | request/plan/manifest/합성을 갱신. 실제 prompt가 같으면 파일 재생성 없이 접근성 문구 검사, brief/prompt가 바뀌면 해당 이미지 재검수 |

낮춘 장수에서 제외된 기존 파일도 삭제하지 않는다. 표시 목록과 보관 파일을 구분한다. 원고 SHA가 달라졌는데 일부 문단만 바뀌었다는 이유로 모든 기존 승인 플래그를 유지하지 않는다.

## 완료 판정과 오류 복구

| 결과 모드 | complete에 필요한 현재 증거 | 제공 파일 |
|---|---|---|
| text-only | 파서 통과·실제 본문 지표·원고 사용 선택 | article.vN.md |
| prompt-only | 확정 원고·N개 계획·슬라이드 문구 검토·구성 사용 선택 | article, request, plan. 실제 이미지가 있다고 표시하지 않음 |
| generate | 위 계획+실제 도구 반환 기록+N개 파일 검사+시각 QA+사용 선택+package_verified | 원고, N장, manifest, 이미지 포함 원고, 검사 기록 |
| use-files | 명시 매핑한 N개 실제 사용자 파일+문맥/시각 QA+사용 선택+package_verified | 위 합성 패키지. provenance=user-file, 생성 실행 기록 불필요 |
| edit-existing | 원본 이미지 binding+실제 편집 반환+파일 검사+변경/보존 조건 QA+사용 선택 | 편집 이미지. 원고 연계 시 기존 이미지들을 포함한 전체 합성 패키지 |

외부 생성 도구가 현재 실행될 수 없으면 원고·계획까지 보존하고 미실행 슬롯을 알린다. status를 complete로 바꾸거나 임의 파일로 채우지 않는다. 패키지 검증 출력의 generation_verified/visual_qa_verified=false는 그대로 유지한다. 세션의 실제 도구/검수 기록과 의미가 다르다.

| 오류/상황 | 동작과 재개 지점 |
|---|---|
| INVALID_ANSWER / STALE_QUESTION | 상태 불변, 현재 질문 다시 제시. 질문마다 다른 계약을 받는 것을 막음 |
| REVISION_CONFLICT / SESSION_BUSY | 덮어쓰기/재실행 없이 최신 session 읽기. 사용자에게 같은 옵션을 다시 답하게 하지 않음 |
| STALE_ARTICLE / ASSET_CHANGED | 변경된 파일을 보존하고 관련 계획·검수로 복귀 |
| SLOT_SHORTAGE / EXPLICIT_SLOTS_REQUIRED | design_slots. N 축소나 일반 이미지 자동 보충 금지 |
| SLIDE_BRIEF_INSUFFICIENT / SLIDE_BRIEF_DUPLICATE | 어댑터 계획 검토 실패. 슬롯 재설계, 필요한 경우 원고 변경 선택 |
| REFERENCE_UNAVAILABLE / UNSAFE_PATH / INVALID_IMAGE | 해당 실제 파일/작업 위치만 확인. 글쓰기 문답 전체 재시작 금지 |
| effect intent만 있고 결과 불명 | 도구 결과·파일을 대조하는 reconcile. 자동 추가 생성 금지 |
| PACKAGE_INCOMPLETE / 합성 불일치 | manifest/파일/합성 검사에서 실패한 부분만 복구. 정상 원고/이미지는 보존 |
